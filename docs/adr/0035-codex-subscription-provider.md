# ADR-0035: A second provider family, for a ChatGPT/Codex subscription

*Proposed.* Builds on [ADR-0027](0027-custom-provider-url.md), which left "Codex OAuth" for later, and on `docs/research/2026-10-codex-oauth-spike.md` (KOP-177). It does not touch [ADR-0005](0005-benchmark-and-ab-methodology.md): a subscription route can never anchor a benchmark number. The owner read OpenAI's terms and said go on 2026-10-12, for personal development use. Whether to accept this design is still the owner's call.

## Context

KOP-177 found that signing in with a ChatGPT subscription is tolerated in practice but not authorized in writing, and that the subscription backend is probably reached through the Responses API, not chat completions. The second point is unverified: it comes from a third party's description and has to be checked with one live call before any code depends on it. If it holds, ADR-0027's `--provider-url` cannot cover this, because that path sends the same chat-completions request to a different host.

**What the code has today.** One seam: `engine.Provider` is a single method, `Complete(ctx, provider.Request) (*provider.Stream, error)`, declared where it is consumed. `provider.Client` implements it for OpenAI-style `POST /chat/completions` with `stream=true`; `provider/mock` implements it by replay. The request type has no header map, no URL and no credential-shaped field, so a client cannot journal a credential by being handed one. `engine/open.go` chooses the client: `Options.Provider` if a caller supplied one, else the custom-URL client, else the OpenRouter client. The stream (`provider.Stream`) is built from chat-completion chunks, keeps the raw transcript verbatim for the recorder, and yields `Delta`s and an assembled `Reply`. Usage carries `CacheRead`/`CacheWrite`. Cost is reported only where the route supplies it and is never estimated (ADR-0021).

So the abstraction already exists at the engine boundary. What is missing is a second implementation behind it, a way to choose it, and a credential source that is not an environment variable.

## Decision

1. **Keep `engine.Provider` as it is.** A second implementation, `provider.CodexClient` (name provisional), satisfies it. The loop, journal, fixtures and tools do not learn a second protocol: translation to and from the Responses API happens inside the client. If the live check in decision 8 shows the backend takes chat completions after all, this ADR collapses to a credential source and a host, and the client below is not written.
2. **The stream stays one type.** A second constructor, beside `NewSSEStream`, reads Responses-API events and yields the same `Delta` kinds (text, reasoning, tool-call fragments, usage, finish) and the same `Reply`. `Stream.Transcript` returns the native bytes verbatim, so a recorded fixture holds exactly what the backend sent. Fixtures gain a `wire` field naming their family (`chat` is the default and what every existing fixture is), and the replay provider decodes by it. No existing fixture or hash changes.
3. **Selecting it: `provider = "codex"` in the user file, `--provider codex` as a flag. Never a repository's file, never an environment variable.** The reasons are ADR-0024's and ADR-0027's: a cloned repository must not decide where your code and your credential go, and an ambient variable is invisible in a diff or a job log. Naming both `provider` and `--provider-url` is a usage error.
4. **Front ends: the REPL and `run --print` only.** `serve` and `mcp` do not accept it. The owner's go covers personal development use; OpenAI's own text and the OpenCode plugin notice both rule out multi-user and commercial use, and cuttlefish is exactly that. A cuttlefish session never picks up one person's subscription by inheriting a process flag. Revisiting this is a new decision with its own ADR.
5. **The credential is read, not stored by kopicode.** The access token comes from Codex CLI's own file, `auth.json` under `CODEX_HOME` (default `~/.codex`), read-only in the first slice (KOP-193). The file must be mode 0600 and owned by the user or kopicode refuses it, naming the path and never its content. The token lives in memory for the session, goes only in the `Authorization` header of requests to the backend host, and is never in the journal, a blob, a log line, a fixture or a test file. The recorder's header allowlist (AGENTS.md) must be shown to drop it. The account id the backend may require is treated the same way. No refresh in the first slice: an expired token is an error that says to run Codex CLI once, not a silent retry. Own login and refresh are a later slice (KOP-195) and need the endpoints and client id confirmed from OpenAI's own documentation, not copied from a third party.
6. **Models: any id the backend accepts, passed through,** as on a custom URL (ADR-0027 decision 3). The resolved configuration is named `codex:<name>` and that name is in the hash preimage, so a subscription run can never pool with a registered arm. No context window and no cost are claimed unless the backend reports them (ADR-0021).
7. **Unpinned, and says so.** There is no provider routing object; the journal records that the run was unpinned and that the route was `codex`, with the host and never a path, query or credential, and anything that reads a journal for a benchmark refuses it (ADR-0005, as ADR-0027 decision 4). GPT models cannot anchor a published number regardless.
8. **Verify before building.** The first card of the implementation makes one live call with a real login and records, without the token: the endpoint and method, whether it is the Responses API, the required headers, the stream's event names, and what a rate-limit response looks like. The result goes in `docs/research/` and corrects this ADR if it is wrong. Nothing else is built until that is done. It needs the owner's subscription login, not OpenRouter credit.
9. **A feature name for clients.** `provider.codex` is added to `features` in `cmd/kopicode/capabilities.go` only if a wire method or field changes; as `serve` and `mcp` do not take it, none does, and nothing is added.

## Rejected

- **Making ADR-0027's URL carry it.** Right if the backend spoke chat completions; wrong if it speaks Responses, and in either case it leaves the credential in an environment variable.
- **Translating Responses events into chat-completion chunks in an `io.Reader`** so `NewSSEStream` is untouched. It would work and it would make the fixture transcript a rewrite of what the backend sent, not the bytes. The recorder's value is that it is exact.
- **Importing the whole of another harness's auth (Hermes's `auth.json`, a keyring).** One source, Codex CLI's own file, is enough to start; others are a decision each.
- **Letting `serve` and `mcp` take it.** See decision 4.
- **Defaulting it on, or into the registry.** It is an opt-in development route, not an arm.
- **A new `engine.Provider` method for credentials or refresh.** Refresh is the client's business, as retries are (ADR-0007 and `engine/provider.go`); the loop must not make policy out of it.

## Consequences

- New: `internal/codexauth` (the read-only file reader, KOP-193), `provider.CodexClient` and its stream constructor, a fixture `wire` field, `harness.Resolve` learning a `codex` path beside the custom one, `engine/open.go` choosing the client, and `requireProviderCredential` learning the Codex source. All of it fails before the lock and the journal, as ADR-0007 decision 4 requires of every credential refusal.
- A GPT model through a different harness path will behave in ways the harness was not measured against. The documentation says this is a development tool, not an arm, as it does for a custom endpoint.
- The work splits into KOP-193 (credential reader), a verification card (decision 8), KOP-194 (the client, 8 points, split after verification if the surface is larger), and KOP-195 (own login and refresh).
- If the live check shows the backend is not the Responses API, KOP-194 shrinks to a host and a header on the existing client.
